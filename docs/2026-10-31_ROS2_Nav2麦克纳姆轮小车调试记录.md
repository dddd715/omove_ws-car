### 2.3 数据流与坐标变换

```text
建图：/scan + 轮速里程计 → SLAM Toolbox → /map + map→odom
导航：保存地图 + /scan + 轮速里程计 → AMCL → map→odom

Nav2 DWB → /cmd_vel_nav → velocity_smoother → /cmd_vel
                                                 ↓
                                      mecanum_kinematics
                                                 ↓
                                     四个轮速控制器
                                                 ↓
                               Gazebo 中四个主动轮与被动滚子
                                                 ↓
                                         /joint_states
                                                 ↓
                                       mecanum_odometry
                                                 ↓
                                      /odom + odom→base_footprint

TF：map → odom → base_footprint → base_link → 雷达/车轮等 link
```

建图和已有地图导航采用两种不同启动模式；已有地图导航由 AMCL 提供 `map→odom`，不同时启动另一套 SLAM 来发布相同变换。Gazebo 真值只用于独立测量，没有替换实际 `/odom` 或 TF。

### 5.3 观察真实车体的前进、横移、旋转

这些命令只在底盘测试阶段执行，先确保周围空旷且没有 Nav2/遥控同时发送速度。每次只执行一种运动；观察的是 Gazebo 中车体，而不是只看轮子动画或 RViz 模型。

前进：

```bash
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.1, y: 0.0}, angular: {z: 0.0}}'
```

横移：

```bash
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.0, y: 0.1}, angular: {z: 0.0}}'
```

旋转：

```bash
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.0, y: 0.0}, angular: {z: 0.2}}'
```

每次观察短时运动后，在该发布终端 Ctrl+C，再发停止指令：

```bash
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.0, y: 0.0}, angular: {z: 0.0}}'
```

`--rate 10` 会持续发布，直到 Ctrl+C；上面的零速度指令是停车，不是“让小车转一段时间”。底盘另有约 0.5 秒无新指令看门狗，不能把它当作可以离开运行中终端的理由。

### 5.5 本次发现的问题：轮子有反馈，但车体低速旋转不足

旧控制模式的联合基线记录：

| 输入（每段 3 个仿真秒） | Gazebo 真实运动 | 轮速里程计 |
| --- | --- | --- |
| 前进 0.1 m/s | 约 0.160 m | 约 0.163 m |
| 横移 0.1 m/s | 约 0.157 m | 约 0.164 m |
| 旋转 0.2 rad/s | 约 −0.052° | 约 3.385° |

单独旋转复查时，0.2 rad/s 的四轮指令约为 ±1 rad/s，但稳态轮速反馈只有约 0.09～0.11 rad/s，车体几乎不转。把控制器更新率提高到 1000 Hz 没有解决问题，因此没有保留该改动。

解决：新场景四个主动轮接入 Gazebo 原生 `velocity_pid`，保留原生 ros2_control 轮速控制器。PID 参数为 `kp=0.5, ki=0.5, kd=0`，积分误差限幅为 `[-2,2]`。具体代码见第 9 节。

正式模型复测：

| 测试 | Gazebo 真实运动 | 轮速里程计 | 两者差异 |
| --- | --- | --- | --- |
| 前进 | 0.3019 m | 0.2991 m | 位置差约 2.8 mm |
| 横移 | 0.2952 m | 0.3025 m | 位置差约 7.3 mm |
| 旋转 | 33.28° | 34.12° | 朝向差约 0.84° |

这是短程、停车后的起终点比较，不是严格同步轨迹标定，更不是实车精度承诺。底盘执行异常是地图错位的风险来源之一，不能由这一项测试推断历史所有地图变形都只有同一个原因。


### 7.4 发送三个目标

点击 `Nav2 Goal`，在白色空闲区域按住并拖动设定目标朝向后释放。

| 测试 | 操作 | 观察要点 |
| --- | --- | --- |
| 近距离 | 前方约 0.5 m 的空闲位置 | Gazebo 车体实际移动并停车 |
| 侧向 | 侧面空闲位置，尽量保持目标朝向不变 | Gazebo 与 RViz 位姿变化一致；确认底盘横移链路有效 |
| 绕障 | 墙角/障碍另一侧可达空闲位置 | 有全局路径，车体沿可行路径绕行，不持续原地停滞 |

启用全向速度并不意味着任意侧方目标都会纯横移，DWB 也可能选择含旋转的轨迹；纯横移能力用第 5.3 节独立指令验证。

不要把目标放进墙体、灰色未知区或明显不足以容纳车身的狭窄位置。必要的短时朝向调整不等于故障；持续无平移并出现进度失败才需要进一步排查。

本次用户在重启并应用修复后反馈可以正常运行；自动定量验收重点是第 8.7 节的固定凹形拐角路线。其他任意目标仍应按现场情况验收。

## 8. 遇到的问题、证据和解决办法

### 8.1 看不到小车/激光，Fixed Frame 报错

**现象：** RViz 空白、`Frame [map] does not exist`，RobotModel、LaserScan 或 Map 状态异常。

**排查顺序：**

1. 确认启动的是底盘模式、建图模式还是已有地图导航模式。
2. 底盘模式使用 `odom`；建图/地图导航才期待 `map`。
3. 检查 `/scan` 是否有数据、`/odom` 是否唯一、相关 TF 是否存在。
4. 导航模式加载正确地图并设置初始位姿，观察 AMCL。
5. 展开对应显示项状态，按具体报错处理。

```bash
ros2 node list
ros2 topic info /scan --verbose
ros2 topic echo /scan --once --field header --qos-reliability best_effort
ros2 topic info /map
```

截图只能提示显示/坐标或数据链路异常，不能仅据此确定是哪个底层程序出错。Gazebo 的蓝色激光射线可视化也不等于 Nav2 地图异常。

### 8.2 新场景图形窗口报 Camera / shader 错误

**线索：** 曾出现 `Unable to find shader lib`、Camera 中 `px != 0` 等图形错误。

**本次处理：** 新场景设置 `GAZEBO_RESOURCE_PATH` 时显式保留 `/usr/share/gazebo-11`，防止覆盖 Gazebo 系统资源回退路径，同时保留原环境变量。

处理位置：`world01_sim.launch.py`。本次证据支持资源路径修复；不能把所有 Camera/GPU 错误都归为这一原因。

### 8.3 低速时轮子在转，车体几乎没转；地图出现拖影

**证据：** 在未启动 SLAM/Nav2 的独立底盘实验中已经复现低速执行不足；轮速指令到达控制器，但反馈显著低于期望，轮速积分与真实旋转不一致。

**处理：** 新场景默认使用 `velocity_pid`，主动轮 PID 增益为 `0.5/0.5/0`，保留 100 Hz 控制器更新率和被动滚子状态接口。修复后先完成底盘复测，再重新扫描和保存地图。

没有采用 Gazebo 真值直接发布 `/odom` 来掩盖问题。提高最小转速虽然可能让某些旋转看起来有效，也不能代替低速段验证。

### 8.4 导航启动报 `name 'false' is not defined`

**用户日志：**

```text
Caught exception in launch: name 'false' is not defined
```

**原因：** 本机 Humble Nav2 的相关条件使用 `PythonExpression(['not ', slam])`。继承来的字符串 `false` 参与表达式时成为 `not false`，Python 不认识小写 `false`。

**处理：** 在已有地图导航的 Nav2 include 中显式传入 Python 风格字符串：

```python
'slam': 'False',
'use_composition': 'False',
'autostart': 'true',
```

这里针对具体的 PythonExpression 参数；不是要求把所有 ROS YAML/launch 中的 `false` 都批量改成 `False`。导航的地图、参数和 `use_sim_time` 同时显式传递。

启动中途失败后还检查了残留子进程，避免再次启动时叠加两套底盘。

### 8.5 一开始发现 `/odom` 有两个发布者

**现场证据：** 存在旧 Gazebo 和重复 `mecanum_odometry`、`mecanum_kinematics`、`robot_state_publisher`；新启动的 gzserver 退出 255，旧实例仍运行。

**风险：** 两套轮速/TF 发布链路混在一起，会使导航接收到不一致状态。

**处理：**

1. 取消当前目标。
2. 核验具体 PID/命令，退出冲突启动和遗留节点。
3. 重新启动后检查 `/odom` 只有一个发布者。
4. 在 `world01_nav.launch.py` 所有子启动之前检查 Gazebo master 端口；已占用就停止本次启动，避免先启动部分新节点再失败。

```bash
ros2 topic info /odom --verbose
ros2 node list
pgrep -af 'gzserver|mecanum_odometry|mecanum_kinematics|robot_state_publisher'
```

端口检查只能防止已有 Gazebo master 时再次启动，不能代替所有残留 ROS 节点检查。排除重复进程后仍出现拐角停滞，因此重复节点不是最后一个问题的完整解释。

### 8.6 RViz 出现 `QBasicTimer::stop`

**用户日志：**

```text
NavigateToPose will be called using the BT Navigator's default behavior tree.
QBasicTimer::stop: Failed. Possibly trying to stop from a different thread
```

第一行说明客户端准备发送导航请求，不是控制失败。第二行是 Qt 定时器/线程相关警告；本次没有证据将它认定为导航停滞的根因。

本次转而读取 `controller_server`、`behavior_server`、`bt_navigator` 日志。实际关键报错为：

```text
Failed to make progress
```

因此不能只根据 RViz 终端的界面警告调整机器人底盘。

### 8.7 有绿色全局路径，但凹形拐角反复原地转动

**现象：** 之前若干路径成功，但某段绕墙路线停滞；RViz 画出了 `/plan`，车体反复旋转/小幅摆动。

**证据：**

- 控制器连续报进度失败；全局路径存在不表示局部轨迹一定能持续推进。
- 失败初期行为服务器没有执行 Spin；DWB 轨迹评分本身就反复选中近零平移、非零转动。
- 随后行为树才可能进入清代价地图、旋转、等待等恢复。
- 独立仿真中同时记录 Gazebo 真值、里程计、AMCL、规划路径和 DWB 评分，复现了同样的停滞。

**固定复现条件：**

| 项目 | 数值 |
| --- | --- |
| 地图 | 本次保存的 `maps/world01.yaml` |
| Gazebo 初始位姿 | `(-1.16, -3.43, yaw=0)` |
| 对应 map 初始位姿 | `(-1.16, -2.43, yaw=0)` |
| map 目标 | `(0.21, -0.11, yaw=0)` |

这些坐标只用于本张地图的诊断，不是任意新地图都适用的初始位姿。

**对照过程：**

| 实验 | 结果 | 是否保留 |
| --- | --- | --- |
| 原 DWB 配置 | 90 秒墙钟时间仍未到达，发生停滞/恢复 | 保留原参数供对照，不再作为默认 |
| 移除方向对齐评分并调整相关评分 | 仍停滞；实验结束时主动中止 | 不保留 |
| 保持原评分项，仅限制局部路径前视 | 成功绕行并返回成功状态 | 保留 |
| 最终配置关闭额外评分输出复测 | 约 30.35 个仿真秒完成，无进度失败 | 通过 |

90 秒是旧配置的墙钟超时，30.35 秒是新配置的仿真运行时间；两者计时口径不同，不能直接算“提升百分比”。

**最终修改：**

```yaml
controller_server:
  ros__parameters:
    FollowPath:
      prune_distance: 1.0
      forward_prune_distance: 0.8
      shorten_transformed_plan: true
```

这是要合入现有 FollowPath 配置的增量，不能用这几行覆盖整个 `nav2_params.yaml`。

该场景的凹形绕行路径在空间上接近，但沿路径还需要先绕远。缩短局部前视长度，让 DWB 的局部目标保持在下一段绕行路径上，避免提前追踪墙另一侧的路径点。对照实验证明这组修改解决了所复现路线，不应扩大为任意地图的通用参数结论。

保留原速度限制、车体轮廓、膨胀半径、DWB 评分项和进度超时；没有通过缩小车身或放宽超时来使测试通过。该 YAML 是共享配置，旧场景也会读取这一调整；旧场景若再次使用，仍应重新验收。

### 9.3 现有逆运动学：车体速度转四轮速度

文件：`src/omove_description/omove_description/mecanum_kinematics.py`。

采用本项目的 X 型麦克纳姆轮符号约定，轮半径 `r=0.076 m`，半轴距 `Lx=0.18 m`，半轮距 `Ly=0.20 m`。核心公式：

```python
        w_fl = (vx - vy - (self.Lx + self.Ly) * omega) / self.r
        w_fr = (vx + vy + (self.Lx + self.Ly) * omega) / self.r
        w_rl = (vx + vy - (self.Lx + self.Ly) * omega) / self.r
        w_rr = (vx - vy + (self.Lx + self.Ly) * omega) / self.r
```

`vx/vy/omega` 分别来自 `/cmd_vel` 的 `linear.x/linear.y/angular.z`。四个轮速按比例统一限幅到 12 rad/s，避免单轮截断改变运动方向；非法数值立即置零。看门狗使用 steady clock，约 0.5 秒没有新指令就发零，仿真暂停也不会阻止清除过期命令。

这是今天排查所依赖的既有速度分配链路，本次没有通过反转运动学符号来处理拐角停滞。

### 9.4 现有里程计：使用反馈轮速，不直接积分期望指令

文件：`src/omove_description/omove_description/mecanum_odometry.py`。

按 joint 名称解析真实反馈，不能假定 `/joint_states` 数组顺序固定。正运动学：

```python
        fl, fr, rl, rr = wheels
        vx = self.radius * (fl + fr + rl + rr) / 4.0
        vy = self.radius * (-fl + fr + rl - rr) / 4.0
        wz = self.radius * (-fl + fr - rl + rr) / (4.0 * self.lever)
```

将车体系速度积分为里程计坐标系位姿，发布 `/odom` 以及 `odom→base_footprint`。含旋转时使用常体速度的精确平面积分：

```python
def integrate_pose(x, y, yaw, vx, vy, wz, dt):
    """Integrate constant body twist exactly, including simultaneous rotation."""
    angle = wz * dt
    if abs(angle) < 1e-8:
        a, b = dt, wz * dt * dt / 2.0
    else:
        a, b = math.sin(angle) / wz, (1.0 - math.cos(angle)) / wz
    dx, dy = a * vx - b * vy, b * vx + a * vy
    x += math.cos(yaw) * dx - math.sin(yaw) * dy
    y += math.sin(yaw) * dx + math.cos(yaw) * dy
    yaw = math.atan2(math.sin(yaw + angle), math.cos(yaw + angle))
    return x, y, yaw
```

还处理重复时间戳、Gazebo 时间回退和无效轮速。本次独立实验中的 Gazebo 真实位姿仅用于对照，不接入这条发布链路。

```python
def require_free_gazebo_master(context):
    """Fail before starting any robot/Nav2 nodes if an old simulation survives."""
    uri = urlparse(os.environ.get('GAZEBO_MASTER_URI', 'http://localhost:11345'))
    try:
        connection = socket.create_connection((uri.hostname or 'localhost', uri.port or 11345), timeout=1.)
    except ConnectionRefusedError:
        return []
    except OSError as error:
        raise RuntimeError(f'Cannot verify Gazebo master is free: {error}') from error
    connection.close()

        'remaining gzserver/robot nodes before starting world01_nav; otherwise '
        'duplicate odometry and TF publishers can corrupt navigation.')
```

### 10.3 发生问题时抓哪些日志

RViz 终端只反映客户端与可视化，不足以解释所有规划控制问题。首先看运行导航 launch 的终端，再查看节点日志。

在本机默认日志目录下，列出最近的相关日志：

```bash
ls -t /home/deng/.ros/log/controller_server_*.log | head -3
ls -t /home/deng/.ros/log/behavior_server_*.log | head -3
ls -t /home/deng/.ros/log/bt_navigator_*.log | head -3
```

根据实际列出的文件名查看，不把日志目录编号写死。若设置了 `ROS_LOG_DIR`，到对应目录查找。

| 日志线索 | 优先检查 |
| --- | --- |
| 地图/TF 不存在 | 启动模式、激光、时间和定位 |
| 没有全局路径 | 地图、目标位置、全局代价地图与 planner_server |
| `Failed to make progress` | 局部控制输出、执行反馈、局部代价地图、DWB 轨迹 |
| behavior_server 正在 `spin` | 发生了旋转恢复；继续追查之前为什么控制失败 |
| `/cmd_vel` 非零但车体不动 | 控制器 active、轮速反馈、接触与碰撞 |
| RViz 在动而 Gazebo 不对应 | 里程计/TF、重复节点、车体真实运动与时间同步 |
| `QBasicTimer` 但导航仍工作 | 记录界面警告，不直接认定为控制根因 |

对单个速度链路进行只读观察：

```bash
ros2 topic echo /cmd_vel_nav
ros2 topic echo /cmd_vel
ros2 topic echo /odom --field twist.twist
```

分别开检查终端或逐个观察后 Ctrl+C。这些是订阅命令，不会给小车发送运动命令。

## 12. 今天的关键经验与后续边界

1. **先底盘，后建图，再导航。** 低速控制与里程计不一致时，先修执行链路，避免只调 SLAM 试图压住地图重影。
2. **看真实运动。** 同时观察 Gazebo 车体、反馈轮速、里程计与 RViz；轮子动画和绿色全局路径都不是闭环成功的充分条件。
3. **将多个问题分开。** 低速执行不足、重复进程、Python 布尔表达式异常、DWB 拐角停滞是不同问题，修掉前一个不代表后面的已经解决。
4. **使用对照实验。** 保留旧参数、相同地图/起点/目标和独立诊断记录，只保留被验证有效的修改。
5. **以运行参数验收。** 源码修改后编译、source、重启，再读取运行时参数；不只检查编辑器里的内容。
6. **今天完成的是本机仿真流程与固定路线验证。** 旧场景、不同出生朝向、其他复杂路线、长时间漂移以及实车控制还需要分别验收。
